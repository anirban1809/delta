# Plan: Phase I — Multi-file Modules (v0.5)

Date drafted: 2026-06-03
Status: planning, not started.
Predecessor: the v0 baseline ([compiler-status.md](../../compiler-status.md)). Phase I is the **first** phase of v0.5a.
Successor: Phase D depends on this landing because `std/log` (Phase J) imports `extern "c"`, and Phases A/B/C/E all benefit from being able to factor code across files.
Spec basis: [spec-sections/01-source-file-convention.md](../../spec-sections/01-source-file-convention.md), [spec-sections/02-compilation-pipeline.md](../../spec-sections/02-compilation-pipeline.md).

## Goal

Promote the compiler from "single .delta file in, single binary out" to "a graph of .delta files — plus an optional `delta.json` manifest — in, single binary out." After Phase I:

```bash
$ delta init                # scaffold delta.json + src/main.delta + .gitignore
$ delta build               # manifest mode: reads delta.json "entry"
$ ./build/debug/bin/main

# …or standalone, no manifest:
$ delta build main.delta    # main.delta imports ./util.delta, exports/imports types
$ ./build/debug/bin/main
```

…works for any acyclic graph of user modules connected by `./relative` import paths, sharing both **values** (`export function`/`const`) and **types** (`export type`) across module boundaries. The `std/...` resolver is wired so future phases can drop stdlib modules in with no further plumbing, but no stdlib modules ship yet (`std/log` lands in Phase J). Incremental compilation, the per-mode cache, and `.delta-meta` static libraries remain deferred (§2.7, §2.11).

## In-scope language surface

- `export` modifier on top-level `function`, `const`, **and `type` declarations** (records + aliases). Non-`export` decls are module-private.
- `import { Name1, Name2 } from "./relative/path";` — relative paths only, must start with `./` or `../`. The same form imports types and values alike (one specifier list, no `import type` distinction).
- `import { Name } from "std/...";` — resolves against the embedded stdlib FS (the resolver lands here; Phase J populates the content).
- Module identity tied to file path relative to the project root.
- Cycle detection in the module graph (error with cycle trace).
- Importing a non-exported name is a structured diagnostic.
- Importing a name that does not exist in the source module is a structured diagnostic.
- Bare paths (anything not starting with `./`, `../`, or `std/`) are rejected with "unknown import root."

## In-scope build surface

- **`delta.json` manifest, parsed as JSONC** (`//` + `/* */` comments, trailing commas). Consumed fields in Phase I: `entry` (build target path) and `build.{debug,release}` (selects the output mode). `name`, `version`, `schemaVersion`, and `target.{backend,standard,compiler}` are parsed and validated but otherwise reserved (no behavior wired yet).
- **`delta init` [--name foo] [--no-src]`** — scaffolds `delta.json` + `src/main.delta` (or flat `main.delta`) + `.gitignore` (`/build`). Never auto-generated by any other command (§1.2).
- **Two build modes**, `debug` (default) and `release`, writing to `build/<mode>/{c,obj,bin}` (§1.6). Mode selected by `--release` (or future manifest default).
- **Project root** = the directory containing `delta.json` when manifest-driven; the entry file's directory in standalone (`delta build <file>`) mode (§1.5).

## Explicitly out of scope for Phase I

| Feature | Reason | Eventual home |
|---|---|---|
| `import { Name as Local }` rename form | Goal-doc non-goal. | Post-v0.5. |
| `import * as ns from "..."` namespace form | Goal-doc non-goal. | Post-v0.5. |
| Re-exports (`export { Name } from "...";`) and barrel files | Goal-doc non-goal. | Post-v0.5. |
| Manifest `target.{backend,standard,compiler}` driving codegen/clang | Parsed + reserved only; clang flags stay hard-coded in Phase I. | Post-v0.5. |
| Manifest `kind: "static-lib"` / `.delta-meta` libraries | Executables only in Phase I. | §2.11 / post-v0.5. |
| Workspaces, custom `srcRoot`, third-party package roots (`npm:...`, vendored deps) | Only `./...`, `../...`, and `std/...`; one `delta.json` per project. | Far post-v0.5. |
| Incremental compilation, persistent module cache, `build/<mode>/cache/` | Every build re-parses every module. | §2.7. |
| Actual stdlib content | Just the resolver in Phase I. | Phase J. |
| `export` on `class` declarations | `class` doesn't exist yet. | Phase E. |

## What's missing today

- Tokenizer has no `import`, `export`, or `from` keywords.
- Parser has no `ImportDeclaration` node, no `Exported` flag on `function`/`const` (an `Exported` field already exists on `TypeDeclaration` but nothing parses or honors it yet).
- `pipeline.Compile(name, contents)` operates on a single in-memory buffer. There's no module graph, no cross-file symbol table, no visibility check.
- Codegen emits one .c file per build with no header. Function `foo` lowers to C `foo`, type `Point` to `struct Point` — no mangling, no cross-TU type sharing. The clang invocation in `internal/toolchain` takes one source file.
- `cmd/delta` reads one file from disk. There is no `delta init`, no `delta.json` reader, no JSONC parser, no build-mode concept (output is flat `build/c/`, not `build/<mode>/`).
- There is no `internal/project/`, no `internal/stdlib/`, no concept of "project root" or "manifest."

## Decisions

1. **Module ID = file path relative to project root, separators replaced with `__`.** `./sub/util.delta` → module ID `sub__util`. The TU filename is `build/<mode>/c/sub__util.c`. Module IDs are computed once during graph construction and threaded through codegen for mangling.
2. **Project root is manifest-aware.** In manifest mode the root is the directory containing `delta.json` and the build target is its `entry` field. In standalone mode (`delta build <file>`) the root is the entry file's directory. Either way, relative imports resolve against the *importing* file's directory; the root only seeds module-ID computation. Workspaces / custom `srcRoot` remain post-v0.5.
3. **Manifest is JSONC, read-only, never auto-written.** A small JSONC reader (strip `//` + `/* */`, allow trailing commas, then hand to `encoding/json`) lives in `internal/project`. Only `delta init` ever writes `delta.json`. Unknown manifest fields are ignored (forward-compat); malformed JSONC or a bad `schemaVersion` is a structured diagnostic. `entry` and `build.{debug,release}` are honored; the rest is parsed-and-reserved.
4. **Stdlib lives in an embedded FS.** Phase I adds the `std/...` resolver wired against a `go:embed` directive pointing at a `stdlib/` directory in the repo. The directory is empty in Phase I; Phase J populates it. Imports against `std/...` that resolve to no file produce "unknown stdlib module" — same diagnostic shape as missing relative imports.
5. **One C TU + one header per Delta module, name-mangled exports, single clang invocation.** Module-private decls are emitted `static`; exported functions/consts get the `delta__<module_id>__<name>` prefix; exported types get `delta__<module_id>__<TypeName>` as their C struct/typedef name. All `.c` TUs are passed to clang in one call: `clang <flags> -o build/<mode>/bin/<entry> build/<mode>/c/main.c build/<mode>/c/sub__util.c …`.
6. **Cross-module *value* references use forward declarations; cross-module *type* references use generated headers.** When module A imports a function/const `foo` from B, A's TU opens with `extern T delta__b__foo(...)`. When A imports a *type* `Point` from B, A `#include`s `build/<mode>/c/b.h`, which holds B's mangled exported struct/typedef definitions. Each module emits exactly one header carrying only its exported type layouts; private types stay inside the `.c`. (This supersedes the original "no headers" stance — pulling type export into Phase I requires struct layouts to cross TU boundaries.)
7. **Cycle detection at graph-build time.** A back-edge during DFS produces "import cycle: a.delta → b.delta → a.delta", one file per arrow.
8. **`export` is parsed as a modifier, not a separate declaration form.** Same approach as TypeScript: a flag on the top-level decl AST node (`function`, `const`, `type`). Not exporting a name leaves it module-private.
9. **Imports must appear before any other top-level declaration.** This is a syntactic restriction with no semantic consequence — but it makes scanning the imports cheap for tooling and keeps the file readable. A diagnostic guides offenders.
10. **The single-file LSP path stays single-file.** `pipeline.Compile` for the language server continues to analyze a buffer in isolation. Cross-module references in an LSP buffer are reported as "unresolved" diagnostics. The "real" LSP module-aware story is post-v0.5.

## Tokenizer changes

- New reserved keywords: `import`, `export`, `from`. Add to the keyword table in [internal/token/token.go](../../../internal/token/token.go) and [internal/tokenizer/tokenizer.go](../../../internal/tokenizer/tokenizer.go).
- No new operators or literal forms.

## Parser changes

- New top-level node `ImportDeclaration`:
  ```go
  type ImportDeclaration struct {
      Specifiers []ImportSpecifier // each carries Name string + Position
      Path       string            // string literal value, quotes stripped
      Position   Position
  }
  ```
- `FunctionDeclaration` and `ConstDeclaration` grow an `Exported bool` flag. `TypeDeclaration` already has the field — the parser must now actually set it from an `export` prefix (today nothing reads it).
- Parsing rule: top-level statements beginning with `import` produce `ImportDeclaration`; encountering an `import` after any non-import top-level declaration is a structured diagnostic "imports must precede other declarations."
- Top-level statements beginning with `export` produce a regular declaration with `Exported = true`. `function`, `const`, and `type` (record + alias) may be exported in Phase I; `export class` is a "not yet supported" diagnostic (Phase E).

## `internal/project/` (new package)

Owns manifest discovery/parsing, project-root resolution, module-ID computation, and output-path layout:

- `type Manifest struct { Name, Version string; SchemaVersion int; Entry string; Target TargetConfig; Build map[string]BuildMode }` — mirrors the JSONC fields. `TargetConfig` and most of `BuildMode` are parsed-and-reserved.
- `func ReadManifest(path string) (*Manifest, error)` — strips `//` and `/* */` comments and trailing commas (a small pre-pass), then `encoding/json.Unmarshal`. Unknown fields ignored; bad `schemaVersion` → diagnostic.
- `func Resolve(arg string) (*Project, error)` — two modes:
  - **Manifest mode:** `arg` is empty or a directory → find `delta.json`, root = its dir, build target = `manifest.Entry`.
  - **Standalone mode:** `arg` is a `.delta` file → root = the file's dir, build target = the file.
  Returns a `Project` carrying `Root`, `EntryRelative`, `Mode` (`debug`/`release`), and the parsed `Manifest` (nil in standalone mode).
- `func ModuleID(projectRoot, absPath string) string` — deterministic path-to-ID mapping; safe as a C identifier component (only `[a-zA-Z0-9_]`).
- `func (p *Project) CDir() / ObjDir() / BinDir() string` — return `build/<mode>/c`, `…/obj`, `…/bin`. Codegen and the CLI use these instead of hard-coding paths, so the `build/<mode>/` layout lives in one place.
- `func Init(opts InitOptions) error` — backs `delta init`: writes `delta.json` (with the §1.2 inline-comment template), `src/main.delta` (or flat `main.delta` under `--no-src`), and `.gitignore` containing `/build`. Refuses to overwrite an existing `delta.json`.

## `internal/stdlib/` (new package, scaffold only)

- `//go:embed stdlib/*` against a `stdlib/` directory at the repo root.
- `func Resolve(path string) (content []byte, found bool)` — looks up `std/foo` → `stdlib/foo.delta` in the embedded FS.
- Phase I ships an empty `stdlib/` directory; the package compiles but resolves nothing. Phase J populates it.

## Semantic analyzer changes

[internal/analyzer/](../../../internal/analyzer/) becomes module-aware. (`internal/semantics/` is deprecated; the live type-checker is the `analyzer.Validator` — its `Scope`/`Symbol`/`Check` are what the module graph builds on.)

- New top-level pass: `ModuleGraph` builder.
  - Input: entry file path.
  - For each unseen file, parse + run the existing single-file analyzer (`analyzer.Validator.Check`, which produces a `Module` value with its symbol table).
  - Resolve each `import` declaration to its source module by:
    1. Relative paths: resolved against the importer's directory.
    2. `std/...` paths: routed through `internal/stdlib.Resolve`.
    3. Anything else: "unknown import root."
  - Bind imported names into the importer's top scope as `SymbolImport` (pointing back to the source symbol). This covers both value symbols (function/const) and type symbols — a `SymbolImport` whose source `Kind == SymbolTypeDecl` makes the imported record/alias usable in type positions and record literals in the importer.
  - Detect cycles via DFS coloring (white/gray/black). On a back-edge, report the full cycle path.
  - Result: an ordered `Project` value with all modules in topological order plus the per-module analyzer outputs.
- New symbol kind: `SymbolImport{Source Symbol; LocalName string; ImportPosition Position}`.
- Visibility check: when binding an `import`, look up the name in the source module's top scope; reject if not found or if `!Exported`. Applies uniformly to functions, consts, and types — importing a non-exported `type` is the same diagnostic as importing a non-exported function.
- Type resolution must follow `SymbolImport` chains: `Validator.ResolveType` / record-literal checking resolve an imported type to the *original* `TypeDeclaration` in the source module so field types and layouts match across the boundary.
- The existing `pipeline.Compile(name, contents)` keeps working for the LSP single-buffer path; a new `pipeline.BuildProject(arg)` is the entry for builds.

## Codegen changes

[internal/codegen/](../../../internal/codegen/):

- `Emit` becomes per-module. It takes a `Project` and a target module ID and emits **two** artifacts: the module's `.c` TU and its `.h` header (the header may be empty if the module exports no types).
- Each module's **header** (`build/<mode>/c/<module-id>.h`) contains, behind an include guard:
  - The mangled struct/typedef definitions for that module's *exported* types only.
  - `#include`s of the headers of any modules whose exported types appear in those layouts (a field of an imported type), so the header is self-contained.
  Private types are *not* in the header; they're emitted inside the `.c`.
- Each **TU** opens with:
  - Standard includes (same as v0).
  - `#include "<module-id>.h"` for its own header, plus one `#include "<dep-id>.h"` per module it imports a *type* from.
  - One forward declaration per imported function/const, using the mangled name.
  - Forward declarations for the module's own exported functions, mangled; private functions unmangled but `static`.
- Definitions follow: private type definitions, file-scope consts, then function bodies.
- Mangling rule:
  - Exported function/const: `delta__<module_id>__<name>` — e.g. `delta__counter__add`.
  - Exported type: the C struct tag / typedef name is `delta__<module_id>__<TypeName>` — e.g. `delta__geom__Point`. References to the type in any TU (fields, params, locals) use this mangled name, so two modules each defining `Point` never collide in a third that imports both.
  - Module-private (functions, consts, types): emitted with `static`/file-local linkage; the Delta-side name stays the same because file scope makes the C-level collision impossible across TUs.
- Entry shim: exactly one module in the graph may define `main`. Zero or two+ are structured errors. The chosen module's TU emits the C-level `int main()` wrapper around `delta_main`.

## Pipeline changes

- New `pipeline.BuildProject(arg string, mode string) (*BuildResult, *ErrorBag)`:
  1. Resolve `arg` (file, directory, or empty) → `*project.Project` via `internal/project`, picking manifest vs standalone mode and reading `delta.json` if present.
  2. Build module graph from the project's build target (parse + analyze each file, detect cycles, check visibility).
  3. For each module in topological order, run codegen → write `<CDir>/<module-id>.c` and `<CDir>/<module-id>.h`.
  4. Locate clang via the existing toolchain probe.
  5. Invoke clang once with every generated `.c` file (headers are found via `-I<CDir>`): `clang <flags> -I<CDir> -o <BinDir>/<entry-basename> <CDir>/*.c`.
  6. Return the binary path or surface diagnostics.

## Toolchain changes

`internal/toolchain.InvokeClang` accepts a slice of source files plus an include-dir argument (`-I<CDir>`) instead of one source file. The flag set is otherwise unchanged from v0.

## CLI changes

- `delta build` (no arg) → manifest mode: read `./delta.json`, build its `entry`. Error if no manifest and no file arg (§1.2).
- `delta build <file.delta>` → standalone mode: `<file>` is the build target; root is its directory.
- `delta build --release` selects the `release` mode (output under `build/release/`); default is `debug`.
- `delta init [--name foo] [--no-src]` → new subcommand, backed by `project.Init`.
- `delta dump-ast <file>` continues to dump a single file's AST. `delta lsp` continues to use the single-buffer `pipeline.Compile`.

## Testing strategy

New fixture format under `test-source/tests/codegen/projects/`. Each project is a directory:

```
test-source/tests/codegen/projects/two_module_ok/
  main.delta
  util.delta
  expected.json   # { "expect": "pass", "exit_code": 7 }
```

The runner walks the directory and runs `delta build` (manifest fixtures) or `delta build main.delta` (standalone fixtures), then asserts on the result.

Module / value fixtures:

- `two_module_ok/` — main imports an exported function from util, calls it.
- `nested_dir_ok/` — main imports `./sub/util`, exercises path normalization and module-ID encoding.
- `cycle_err/` — a.delta imports b.delta, b.delta imports a.delta; expect cycle diagnostic.
- `non_exported_err/` — util declares `add` without `export`; main imports it; expect visibility diagnostic.
- `missing_name_err/` — main imports a name util does not declare; expect "name not exported."
- `bare_path_err/` — main imports `"foo/bar"`; expect "unknown import root."
- `std_unknown_err/` — main imports `"std/nonexistent"`; expect "unknown stdlib module."
- `same_name_collision_ok/` — two modules each define a private `helper`; no collision because `static`.
- `import_after_decl_err/` — `function f() {}` then `import {...}`; expect "imports must precede other declarations."

Type export/import fixtures:

- `export_type_ok/` — geom.delta `export type Point = { x: i32, y: i32 }`; main imports `Point`, constructs a record literal, reads a field; expect correct exit code (exercises header emission + type mangling).
- `non_exported_type_err/` — geom declares `type Point` without `export`; main imports it; expect visibility diagnostic.
- `type_field_of_imported_type_ok/` — module C's exported type has a field of module B's exported type; main imports C; verifies the generated header `#include`s B's header.
- `same_type_name_collision_ok/` — two modules each export `type Point` with different layouts; a third imports both under no name clash via distinct mangled tags `delta__a__Point` / `delta__b__Point`.

Manifest / build-system fixtures:

- `manifest_build_ok/` — `delta.json` with `entry: "src/main.delta"`; `delta build` (no arg) resolves the entry and builds into `build/debug/bin/`.
- `manifest_jsonc_ok/` — manifest with `//` comments and trailing commas; verifies the JSONC reader.
- `init_scaffold_ok/` — run `delta init`, assert `delta.json` + `src/main.delta` + `.gitignore` exist and the scaffold builds.
- `release_mode_ok/` — `delta build --release` writes to `build/release/` and runs.
- `no_manifest_no_arg_err/` — `delta build` in a dir with no `delta.json` and no file arg; expect a clear "no manifest / no source given" diagnostic.

## Stage-by-stage implementation order

1. **Tokenizer + parser**: keywords, `ImportDeclaration`, `Exported` flag on `function`/`const`/`type`. Parser tests for accepted/rejected forms (including `export type` and `export class` → diagnostic).
2. **`internal/project/`**: manifest discovery + JSONC reader, standalone/manifest `Resolve`, module-ID computation, `build/<mode>/` path helpers. Unit-test deterministic module IDs and JSONC parsing.
3. **Module graph builder** in `internal/analyzer/`: parse + analyze each file once, resolve imports, detect cycles. No codegen yet; expose the project as a value.
4. **Cross-module symbol resolution**: `SymbolImport` for values *and* types, visibility check, imported-type resolution through `ResolveType`.
5. **Codegen rework**: per-module `.c` + `.h` emission, function/const/type mangling, value forward decls, header includes for cross-module type layouts.
6. **Pipeline + CLI**: `BuildProject` entry point (manifest + standalone), `delta init`, `--release` mode, clang invocation with multiple TUs and `-I<CDir>`.
7. **`internal/stdlib/` scaffold**: `go:embed` of an empty `stdlib/` directory, `std/...` path resolver.
8. **Fixture suite**: land all module, type, and manifest fixtures.

Steps 1–2 are mechanical. Step 3 is the structural milestone (the analyzer becomes module-aware). Steps 4–6 ride on top. Within step 5, land function/const mangling first, then layer in the header-based type sharing — it's the one genuinely new codegen mechanism.

## Risks and open questions

- **`pipeline.Compile` vs `BuildProject` divergence.** The LSP path stays single-file; the build path is project-aware. Risk that the two drift in invariants over time. Mitigation: `BuildProject` calls `pipeline.Compile` per file under the hood, so the inner loop is shared.
- **Symbol mangling stability.** Module IDs are derived from paths; renaming a directory changes the mangled name. Fine for v0.5 — we don't ship binaries across builds. Add a `// not ABI-stable across renames` comment to the codegen output.
- **Two private symbols sharing a name across TUs.** Both are `static`, so clang's linker never sees them. Tested by `same_name_collision_ok`.
- **Topological-order codegen.** Strictly speaking the order doesn't matter because every TU forward-declares what it references. Emit in topological order anyway so generated .c diffs are stable.
- **`SymbolImport` chains.** Re-exports aren't supported, but an `import` of an `import` is — does the chain bottom out? The visibility check resolves to the *original* declaration; if any link in the chain is non-exported, the import fails at that link.
- **Header layout consistency / ODR.** Every TU that uses an exported type pulls the *same* generated header, so all TUs see one definition of `delta__<mod>__Point`. Risk is only if codegen emits a type's layout two different ways; mitigation: a single `emitTypeLayout(typeID)` helper is the sole producer of a struct definition, used for both the header and any private fallback.
- **Header include cycles.** Type-layout headers `#include` each other when types reference types across modules. Because the *type* graph is acyclic (it rides the import DAG) the includes are acyclic too, but each header still carries an include guard as defense-in-depth.
- **JSONC parsing edge cases.** The comment/trailing-comma pre-pass must not corrupt `//` or `/* */` sequences inside string values. Mitigation: a tiny state machine that tracks string context rather than a blind regex; covered by `manifest_jsonc_ok` plus a unit test with `//` inside a string.
- **Manifest schema evolution.** `schemaVersion` is validated now (reject unknown majors) so future workspace/`kind` fields can be added without silently misparsing old behavior.

## Definition of done

- `delta build` (manifest mode) and `delta build <file>` (standalone mode) both produce a runnable binary under `build/<mode>/bin/` whose exit code matches the fixture's expected value.
- All module, type-export/import, and manifest fixtures pass.
- Single-file v0 fixtures continue to pass unchanged.
- `delta init` scaffolds a project that builds and runs out of the box.
- Importing a non-exported, missing, or bare-path name — value *or* type — yields a precise diagnostic with file:line:col.
- A type exported from one module can be constructed and field-accessed in another, with two same-named types from different modules coexisting via distinct mangled tags.
- A cycle of any length is detected and reported with one file per arrow.
- The Phase D plan can begin without revisiting any module-graph, manifest, or type-export decision.
